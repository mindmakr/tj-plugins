01 What it is

Six clean building blocks — one shared security contract.

A single open index for everything that extends a tinyjump app. Packages live in their authors' repositories; mindmakr/tj-plugins holds the pinned manifests, automated review pipeline, and public request board.

Libraries (library)

Pure, typed .tj modules with zero native code — currency math (tj:money), CSV parsing, URL slugs, deterministic validators, and UI helpers.

Pure · offline · zero permissions

Device Plugins (device-plugin)

Opt-in hardware access across Web, Android, and iOS — tj:camera, tj:location, tj:files, tj:notifications — with canonical permissions auto-wired into mobile builds.

Opt-in · 0 B if unused

Compliance Packs (compliance-pack)

Data-only regional privacy & regulatory rules — like gdpr-eu (EU GDPR) and pdpl-sa (Saudi Arabia PDPL) — checked statically by tj check --compliance.

Data-only JSON · extensible

MCP Plugins (plugin)

Every existing MCP server (databases, payments, search, AI models) works as a typed tinyjump plugin in its own process, with secrets kept safely on the server.

Isolated process · server secrets

Agent Ports (port)

Popular libraries ported from other ecosystems by humans or AI agents — carrying the original library's test suite as objective proof of correctness and staying within size budgets.

Upstream test suite verified

Bridges (bridge)

Typed connectors to REST/OpenAPI specs (tj bridge openapi), HMAC webhooks, SQL databases, queues, and ERP/CRM systems so teams adopt tinyjump piece by piece.

Works alongside legacy stacks
02 Why it is

Starting fresh without supply-chain chaos.

Modern software ecosystems routinely pull hundreds of un-audited transitive packages with full network and filesystem access. In an agentic world where code moves at machine speed, package trust must be enforced by the toolchain, not hope.

Every package shows its permissions like a phone app store — and the compiler refuses to build if the code tries to touch a host, plugin, device sensor, or PII category it never declared.

A brand-new runtime has no legacy dependencies. That is a deliberate advantage: every library in tj-plugins can be tiny, strictly typed, free of obfuscated install scripts, and verified against both its source commit and exact SHA-256 hash.

And because regional compliance packs (like EU GDPR and Saudi PDPL) live in the same open registry, clinics, startups, and public institutions everywhere get machine-checked privacy compliance out of the box — not locked behind expensive enterprise consultancies.

App-Store Permission Model

Zero silent side effects

Before tj add writes a single byte to .tj-packages/, it audits the package AST against four explicit permission surfaces:

network: [https hosts] plugins: [mcp / device] pii: [data categories] device: [camera, location...]

Aliased fetch/plugin calls, plain http:// URLs, dynamic host strings, or undeclared @pii access fail closed at check time — and tj retro flags any tampered or advisory-flagged lockfile entry immediately.

Your app chooses its own bar with tj check --min-trust verified or --min-trust official. Community PRs can never self-assign elevated trust marks — CI rejects them automatically.

04 What it can · Build & Publish

Ship a library, port an upstream package, or bridge any API in minutes.

Built for both human authors and coding agents. Submit one small JSON manifest in a pull request — the review workflow checks everything publicly and publishes on merge.

index/example-pkg.json 1 manifest PR 
{
  "name": "example-pkg",
  "kind": "library",
  "version": "1.0.0",
  "trust": "community",
  "source": "https://github.com/you/tj-example-pkg",
  "entry": "plugin.tj",
  "commit": "<40-char lowercase git sha>",
  "sha256": "<64-char lowercase sha256>",
  "license": "MIT",
  "publisher": "your-github-handle",
  "permissions": {
    "network": [], "plugins": [],
    "pii": [],     "device": []
  }
}

1. Validate locally before opening a PR

Run the exact same validator CI uses — checks manifest schema, license, typosquats, compilation, and AST permissions.

tj registry check index/example-pkg.json --index index --source plugin.tj

2. Turn any OpenAPI 3.x spec into a typed bridge

Generates a compile-checked .tj REST client with literal HTTPS host prefixes plus a ready-to-submit registry manifest.

tj bridge openapi api.json --out plugin.tj --manifest index/my-api.json

3. Request a library, agent port, or bridge

Need something missing? Open a structured request issue so humans or coding agents can pick it up and port it with upstream tests as proof.
